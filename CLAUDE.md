# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Required Reading Before Writing Code

**Before writing or modifying any script, read `docs/CODE_RULES.md` first.** It defines the mandatory folder structure (`Assets/_OneTapImmortal/Scripts/` layout), C# naming conventions, architecture rules (ScriptableObject-driven balancing data, logic/presentation separation, central run state machine, object pooling), and Unity-specific do/don'ts. Notably: no runtime bootstrapping — no `AddComponent`/`GetComponent`; every system must exist as an object in the scene or a prefab, with all references wired via `[SerializeField]` in the Inspector (streamed assets are the one carved-out exception: still a serialized field, but a weak `AssetReference` loaded through `Utils/StreamedAsset<T>` — see the Addressables section). It also mandates performance-first patterns: zero GC allocation in hot paths, manager-ticked updates instead of per-object `Update()`, prewarmed object pools, and split Canvases for uGUI. All first-party code must follow it.

## Project Overview

**One Tap Immortal** (Vietnamese title: **Nhất Niệm Thành Tiên**) — a one-button cultivation (tu tiên/xianxia) roguelite auto-battler in Unity. The player taps a single CULTIVATE button to advance the Cycle (Chu Thiên); each tap rolls a weighted random event (battle, fortune, choice, spring/trap/treasure, artifact sidekick). Battles resolve automatically on a fixed beat; depth comes from build decisions (technique cards + artifact stack) and HP management between fights. 30 rounds per realm (World), then ascend to a new palette and higher difficulty. Death ends the run (reincarnation); best score is saved. The theme brief is `docs/THEME_Immortal.md`; the game was re-themed from "Cosmic Critter Quest" — **`docs/THEME_MAPPING.md` is the old→new lookup for every identifier, content id and term** (read it when touching anything that predates the re-theme, including the design spec).

- **Unity version:** 6000.3.9f1 (Unity 6) — URP (2D Renderer), new Input System, uGUI + TMP
- **Current state:** fully playable. All first-party code lives under `Assets/_OneTapImmortal/Scripts/` (folders per CODE_RULES: Core/Events/Combat/Enemies/Progression/Sidekicks/Worlds/UI/Data/Save/Audio/Utils, editor tooling in `Scripts/Editor/`), namespaces `Game.*` (deliberately theme-agnostic so the codebase can be reskinned again).
- **Main scene:** `Assets/_OneTapImmortal/Scenes/Main.unity` (portrait 1080×1920 — set the Game view to that resolution)

## Code Map & Architecture Facts

- **`GameManager`** (`Core/`, execution order −100) is the only hub: state machine `Ready/Traveling/Battling/Choosing/Dead`, ticks every system from its single `Update` (BattleEngine, stage view, floaters, bursts, tribulation FX, shaker, background, UI). Pure-logic classes (`BattleEngine`, `EventRoller`, `PeacefulEventResolver`, `EnemyFactory`, `XpSystem`, `SidekickRoster`, `RunState/PlayerState/EnemyState`) have no Unity scene dependencies; views listen to C# events.
- **Config assets** live in `Assets/_OneTapImmortal/Data/` (`GameConfig.asset` = every balance knob incl. feel timings; `NarrativeConfig.asset` = the localization **term key** of every flavor line/name pool, the realm-name ladder and the glyph charset; per-item assets under `Upgrades/`, `Fortunes/`, `Sidekicks/`, `Worlds/`, `Meta/`). Upgrades/fortunes are data-driven `StatMod[]` interpreted only by `StatModApplier` — a 9th technique card is a new `.asset` plus two CSV rows, zero code. `GameConfig` keeps `[FormerlySerializedAs]` on fields renamed in the re-theme (`_planets`→`_worlds` etc.) because the asset's numeric tuning is never regenerated — do not remove those attributes.
- **All art is procedural but baked at build time, never at runtime.** `Scripts/Editor/Painter.cs` + `Scripts/Editor/SpriteBaker.cs` (editor assembly) paint every sprite and write them as `.png` assets to `Assets/_OneTapImmortal/Art/Generated/`; the builder wires them onto prefab `SpriteRenderer`s. Runtime views own zero painting code — they only swap sprites and toggle renderers. The hero is a cultivator (ivory robe, jade trim, topknot, ivory-jade sword). Enemies (demon beasts) are assembled from **layers** (glow / horns / spikes / body / spots / eyes / mouth): `EnemyView.Init` picks `_bodySprites[ColorIndex]` + `_eyeSprites[Eyes-1]` and enables the optional layers — the glow layer is the vermillion-violet "demonic qi" elite marker, gold spikes mark bosses. Every realm's backdrop is the single authored painting `Art/Immortal/azure_side_scroll_v3.png` (the baked per-realm procedural skies read as off-theme and were removed), repeated as a mirrored belt by `WorldBackgroundRenderer` so it scrolls seamlessly; `SpriteBaker.PaintSky` survives only as the per-realm fallback when the authored file is missing (baked fallback names key on the **asset name**, `bg_World_*_sky.png`, never the localized DisplayName). Artifact orbs live on their `Sidekick` asset (`OrbSprite`) — one silhouette per id (flying sword / lingzhi / turtle shell / thunder pearl), no faces. Audio is synthesized at runtime (`Audio/SfxSynth`, in `AudioManager.Awake`) — see the audio bullet below.
- **Fonts:** UI uses the FantasyHero pack's `AfacadFlux-ExtraBold` static SDF via a **project-owned copy** at `Assets/_OneTapImmortal/Data/UI/Display SDF.asset` (made by `LoadOrCopyPackFont` — the pack asset itself is never modified). It has no Vietnamese glyphs, so the builder generates dynamic `RobotoVN SDF` from `Assets/_OneTapImmortal/Data/UI/Fonts/Roboto-Bold.ttf`, wires it as the display font's **fallback** (covers stray glyphs like `·`), and `LocalizedFontView` (on the `UI` object, wired with every `TextMeshProUGUI`/`TextMeshPro` in the scene) swaps the whole game to RobotoVN whenever the language code is in `_wideCharsetCodes`. World-space text swaps its outlined material (`WorldText.mat` ↔ `WorldTextVN.mat`, regenerated by the builder from each font).
- **Sprite atlases are code-driven** (`Scripts/Editor/AtlasConfigurator.cs`, menu **Tools ▸ Game ▸ Atlases ▸ Sync**, also run by Build Game (Full)): two folder-packable Sprite Atlas V2 assets in `Assets/_OneTapImmortal/Atlases/` — `Atlas_UI` packs `Textures/` (compressed, like its Layer Lab sources) and `Atlas_Gameplay` packs `Art/Generated/` (uncompressed, keeping the baked pixels exact). The `.spriteatlasv2` files are rewritten on every sync — never edit them by hand. The sync also forces every packed **source** importer to Uncompressed (only the atlas page ships; compressed sources would bake artifacts into the page). `Art/Immortal` is deliberately not atlased: the backdrop streams via Addressables (atlasing it would ship it twice) and the pose sheets are already packed textures.
- **Builder:** menu **Tools ▸ Game ▸ Build Game (Full)** (`Scripts/Editor/GameBuilder.cs`) imports the localization CSV, then regenerates config assets, the baked art in `Assets/_OneTapImmortal/Art/Generated/`, prefabs (`Assets/_OneTapImmortal/Prefabs/`) and the whole wired scene. Idempotent; it overwrites the scene + content arrays/icons/keys, but leaves numeric tuning on an existing `GameConfig.asset` untouched. Changing an enemy color, a realm palette or any painting code requires a rebuild to re-bake the .png. After hand-editing scene objects, know that a rebuild discards those edits — prefer editing prefabs/configs, or extend the builder. The builder never deletes stale outputs — after renaming a content id, delete the orphaned `.asset`/`.png` yourself.
- **Travel leg (adventure feel, not in the spec doc):** CULTIVATE no longer fires the event immediately — it enters `Traveling`, where the hero hops in place (`HeroView.SetWalk` on the `Rig` child) while the ground strip scrolls left; the event fires on arrival. Tapping again cuts the leg short. Beasts then slide in from off-screen right. Knobs: `GameConfig.TravelDuration/TravelDistance/WalkHopsPerSecond/EnemyEnterDuration/EnemyEnterOffset`.
- **Tribulation FX** (`Combat/TribulationFxView`, scene object `TribulationFx` + its own topmost `Canvas_Flash` with **no raycaster**): three pooled jagged-bolt sprites (`fx_bolt.png`) plus a full-screen flash, everything disabled at rest, ticked from `GameManager.Update`. Fired on boss (realm-lord) intros at full intensity and on breakthroughs at 0.7.
- **Audio is pentatonic by construction** (`Audio/SfxSynth`): a gong–shang–jue–zhi–yu ratio table with a degree-indexed `Note` helper, a plucked-string primitive (guzheng color) and a lowpassed rumble (thunder). The per-realm music loop is an open root/fifth/octave drone (no third) plus a slow plucked melody defined as `World._melodyDegrees` (one pentatonic degree per loop slot, −1 = rest, set by the builder; melody tails wrap the loop seam). Realm roots sit on the G pentatonic (G A B D E). Boss sting = temple bell over thunder; breakthrough = sweep + artifact ring.
- **Meta progression (Cultivation Path) — the only thing that survives death.** `MetaState` (`Progression/`, saved under `meta`) holds **spirit stones** (shards in code) plus the ranks bought with them. Stones are paid out twice: immediately on a realm clear (`ShardsPerWorldClear × realm number`, announced inside the `Narrative/WorldClear` line via the `{n}` token) and as a lump sum when the run ends (`ShardsPerRound × score` + elite/boss bonuses, shown on the death screen). Ranks are `MetaUpgrade` assets in `Assets/_OneTapImmortal/Data/Meta/` — the six steps are the cultivation realms (BodyTempering → QiRefining → Foundation → GoldenCore → NascentSoul → SpiritSevering), same `StatMod[]` data as technique cards, applied once **per owned rank** by `RunState.CreateNew`, which is the only place meta touches a run (a resumed `run` save already has them baked into its stats, so it is never boosted twice). Rank *n* costs `CostBase + CostStep × n`.
- **Realm names per level** (presentation only): `NarrativeConfig.RealmKey(level)` maps each 10-level bracket to a `Realm/*` key (Qi Refining … Tribulation Crossing). Breakthrough suffixes bind it as the `{realm}` token; the profile overlay leads its level line with it. `XpSystem` knows nothing about realms.
- **Navigation follows the mobile-game convention, and the layout numbers come from it.** The bottom third of a tall phone is the reachable zone, so every primary control lives there. `UI/NavBarView` is a 4-tab strip (Path / Profile / Records / Settings) parented **into the main menu**, so it exists on the front screen and *only* there — the run screen stays uncluttered and the HUD's home button (top-right, next to the gear) is the one tap back. The strip is **150 px tall — ~50 dp at this canvas, above the 48 dp minimum touch target** — and the whole tab is the button, not just its icon; don't shrink it. The Path tab carries the one badge dot in the game (`MetaState.HasAffordableStep`, refreshed in `ShowMenu` since that is the only time it is visible).
- **`OverlayView` is the single panel shell** — settings, profile, records and game over are all the same component, and new panels should be too rather than new canvases. It follows the reference pattern: title + body + up to 6 action buttons on the card, and a round **✕ hanging below** the card (thumb-reachable, never covering content) which raises `CloseRequested`. The card **sizes itself to its content** (`Layout()`), so a short panel has no dead space; the button block it reserves is `bottom margin + (n-1) pitches + one whole button height` — computing it as `n × pitch` under-reserves and the body text ends up behind the top button. There is no "resume" row anywhere: the ✕ closes.
- **The game boots to a main menu** (`UI/MainMenuView`, canvas order 28), not straight into the run: `Start` builds/loads the run as before and then covers it with the front screen, which simply unpauses on *Continue*. **It is laid out as a home screen, not a list of menu entries** — status chips along the top (tappable profile chip + spirit-stone count), a banner naming the realm and round with the record under it, the hero and realm as the art, then **one big CTA** with the destructive "Reincarnate" demoted to a smaller button beneath it, and the tab bar at the bottom. Everything else is a tab or a panel; resist adding a fifth stacked button. The menu is only a **scrim** — `UIController.ShowMenu` parks the HUD and console canvases so the realm and the idling hero become the art, and its own "Deck" plate stands in for the console panel (same 940 height, so the horizon lands where it does in play). `GameManager.ShowMenu` also hides the floating bars (`BattleStageView.SetBarsVisible`) and, **only when the run is already dead**, the beast — a paused battle keeps its beast because it is still that life's stage. Reachable in play from settings ▸ *Main menu* and from the death screen.
- **The Cultivation Path is reached from the nav bar, the main menu and the death screen** — deliberately never from settings. Settings is Music / SFX / Language / *Main menu* / Restart, and that 4th slot is passed `null` when the menu is already the screen underneath (`OverlayView` hides unlabelled buttons). Because settings can be opened *from* the menu, `HideOverlay` restores `OverlayKind.Menu` rather than `None` when the menu is still up — that is what keeps a language switch re-rendering the right screen.
- **The path is a screen, not a menu** (`UI/MetaPathView` + `MetaNodeView`, its own **opaque** canvas at sorting order 25, reached from the main menu and the death screen; `UIController.IsModalOpen` — overlay, path or menu — is what pauses the run while any of them is up). It draws **one continuous path** climbing a rail up the left side, one rune medallion per step with its detail strip beside it — the array order of `GameConfig.MetaUpgrades` *is* the climb order, bottom to top, and `GameBuilder.ChainSteps` gates each step on the previous one being finished. **Re-shape the path by editing that asset data in the builder, never the layout code** (`BuildMetaPathCanvas` derives every position from `StepY(i)`).
- Three things carry the feel and are easy to break: the rail segment between two steps **fills gold in proportion to the lower step's rank**, so the path visibly charges up (`_railFills` sized against `_railLengths` — set `sizeDelta.y`, not a scale); `_rankIcons` holds the six rarity tiers of one Layer Lab rune motif and `MetaUpgrade.RankIcon` spreads `MaxRank` across them, so a finished step visibly ascends in grade and `MaxRank` need not equal the tier count; and exactly one step is ever unlocked-but-unfinished, which `Refresh` marks as the focal point (brighter strip, soft gold aura, and a pulse driven from `MetaPathView.Tick` when it is affordable). Step strips must stay **opaque** — a translucent one lets the rail behind it tint its edge. `GameConfig.MetaUpgrades` must have exactly as many entries as the built path has steps; `ValidateReferences` errors otherwise, because an extra step would silently never render.
- Save keys: `run`, `best`, `meta`, `music`, `sfx` and `I2 Language` (written by I2, not by `SaveSystem`) — all PlayerPrefs. Speed changes made mid-battle are deliberately not persisted until the next between-events save.
- Play-testing without clicking: drive `GameManager` private members via `mcp__UnityMCP__execute_code` reflection (`OnEngagePressed`, `OnChoicePicked(int)`, fields `_state`, `_run`); set `Application.runInBackground = true` first.

## Localization (English + Vietnamese, I2 Localization)

**`Assets/_OneTapImmortal/Localization/Localization.csv` is the single source of truth for every player-facing string.** Columns: `Key,English [en],Vietnamese [vi]` — add a language by adding a column (`Japanese [ja]`), nothing else. `Assets/_OneTapImmortal/Resources/I2Languages.asset` is a **generated cache** of that CSV; never hand-edit it, and never rename it (I2 loads it by its Resources name).

- **Workflow:** edit the CSV → **Tools ▸ Game ▸ Localization ▸ Import CSV** (Ctrl+Shift+L). `Import` runs in `Replace` mode, so a key deleted from the CSV disappears from the game, and it logs any language with empty cells. **Export CSV** dumps the asset back out (full I2 `Key,Type,Desc,…` header) for the case where someone edited terms in the I2 window instead. `Build Game (Full)` imports first, so a rebuild never ships stale text.
- **No literal player-facing string may be written in code or in the builder.** Everything goes through `Game.Localization`: `Loc.Get(key)` / `Loc.Format(key, args)` / `Loc.Pick(keys)`, keys as constants in `LocKeys`, or — for narrative pools — the key arrays on `NarrativeConfig`. `Loc` is the only file that references `I2.Loc`. A missing key renders as the key itself plus a `[Loc] Missing term:` warning.
- **`LocLine` (key + up to 3 token substitutions) is how console text is stored**, not a finished string: `GameManager._eventLines` holds up to 3 of them (line + suffix + tail, e.g. win text + breakthrough + realm-cleared) so `OnLanguageChanged` can re-render the *same* sentence in the new language instead of rolling a fresh random one. `EventOutcome.Line/Suffix` carry them out of the resolvers. Banners live ~3 s, so their text is resolved eagerly and is not re-rendered.
- **Language switching** is the 4th button of the settings overlay (reachable from the main menu or the in-game gear) (`Loc.CycleLanguage`, wraps through the languages in the source). I2 batches the switch by one frame, then `Loc.Changed` fires; `GameManager.OnLanguageChanged` re-applies the font, static captions (`UIController.RefreshStaticText` → `HudView`/`ConsoleView.RefreshStaticText`, `EngageButton.RefreshLabel`), run values, the console line and whichever modal is open — settings, death, profile, records or the Cultivation Path (tracked by `GameManager._openOverlay`). **The front screen is refreshed separately, on `Menu.IsOpen` rather than on `_openOverlay`** (`RefreshMenu`, split out of `ShowMenu` so it re-sends the values without closing what sits on top): settings/profile/records all open *over* the menu, so keying it off the top modal left the CTA, the level chip and the realm/round line frozen in the old language. Views that cache a format string for allocation-free `SetText` must re-pull it there.
- **Text length is a real constraint** — the stats-bar captions and the CULTIVATE label sit in fixed-size pills, and Vietnamese runs ~20 % longer than English. Check the 1080×1920 Game view after changing them.
- `Localize` components are not used anywhere; every string is set from code. (I2's import did set the `TextMeshPro` scripting define, so they would work if ever needed.)

## The Design Spec Is Authoritative

`docs/COSMIC_CRITTER_QUEST_Game_Design_Spec.md` (written in Vietnamese, kept under its original name) defines all gameplay rules, formulas, and tuning direction — the re-theme changed no mechanics, so it still governs; read it together with `docs/THEME_MAPPING.md` for the current names. The most load-bearing rules:

- **One button.** Tap CULTIVATE → Cycle +1 → roll one weighted event. The only other player decision is the occasional 3-card technique choice. Do not add extra input mechanics.
- **Event roll** uses `EVENT_WEIGHTS` with an anti-boredom guard: more than `MAX_NONBATTLE_STREAK` (2) consecutive non-battle events forces a battle (effective battle rate ~55-60%).
- **Combat** is turn-based on a `BEAT_MS` beat (hero first, alternating). Damage = `atk × rand(0.85–1.15) − def`, minimum 1. Hero regens 12% maxHP after each won fight. **Enrage** (sát khí): past 40 beats in one fight, enemy damage +5%/beat — infinite-sustain stalemates must stay impossible.
- **Enemy scaling** is driven by the global difficulty `g = world×30 + round` (polynomial × 1.015^g exponential); every run must end eventually. Boss every 10th round (HP ×1.8, ATK ×1.15, XP ×3); elites 12% chance.
- **Sidekicks (artifacts)** are passive, max 3 held — picking a 4th always means dropping one. 8 technique cards including deliberate trade-off and situational cards.
- **All balance numbers live in the central config** (ScriptableObject, per CODE_RULES) — the spec's `EVENT_WEIGHTS`/`ENRAGE`/`PLAYER`-style names map to config fields. Tune there, never scatter constants in code.
- **Save**: `run` (written only between events, never mid-fight — reloading mid-fight restores the pre-fight state) and `best` (total global rounds, overwrite only when higher).

The spec ends with a tuning guide ("Hướng tuning") — when rebalancing, follow those levers (e.g. adjust `ENEMY.hp/atk` first, keep player stats fixed) instead of inventing new ones.

## Working with Unity

The Unity Editor is automated via **Unity MCP** (`mcp__UnityMCP__*` tools — the `com.coplaydev.unity-mcp` package). Use it rather than asking the user to click through the editor:

- Compile-check after script changes: `mcp__UnityMCP__validate_script` and `mcp__UnityMCP__read_console` (check for errors before declaring work done).
- Run tests (Unity Test Framework is installed): `mcp__UnityMCP__run_tests` (edit/play mode).
- Scene/GameObject/prefab/asset manipulation: `manage_scene`, `manage_gameobject`, `manage_prefabs`, `manage_asset`, etc.
- If UnityMCP tools are missing or disconnected, the `unity-mcp-connect` skill diagnoses and fixes the connection (each open editor uses its own port).

## Shipping the WebGL build

**Menu Tools ▸ Game ▸ Build WebGL (Release) / (Development) / Build And Run WebGL (Development)** (`Scripts/Editor/WebGLBuilder.cs`) is the only supported way to build. Output goes to `Builds/WebGL/{Release,Development}` (gitignored); the log prints a per-file payload table (that, not total size, is what explains a slow first load). Do not build from the Build Settings window — you would get whatever Player Settings happen to be lying around.

**These Player Settings are owned by the build tool and rewritten on every build — editing them by hand is pointless, the next build overwrites them:**

| Setting | Value |
|---|---|
| `productName` | `One Tap Immortal` (const in `WebGLBuilder`) |
| `companyName` | `Imba` (const in `WebGLBuilder`) |
| `WebGL.template` | `PROJECT:PortraitGame` |
| `defaultWebScreenWidth/Height` | 1080 × 1920 (the template reads these as `{{{ WIDTH }}}`/`{{{ HEIGHT }}}`) |
| `defaultInterfaceOrientation` + autorotate flags | Portrait only |
| `WebGL.compressionFormat` / `decompressionFallback` | Brotli + fallback for Release, Disabled for Development |
| `WebGL.dataCaching` | on |

To change any of them, edit the constants in `WebGLBuilder.cs`. **`productName` and `companyName` derive the WebGL save path** — changing either after the game is deployed orphans every player's `run`/`best`/`meta`. Both were settled (pre-deploy) during the re-theme; treat them as frozen once the first public build ships.

**Portrait lock has three layers, and all three must agree** — fixing one still leaves other hosts framing the game wrong:

1. `Assets/WebGLTemplates/PortraitGame/` sizes the **canvas element** (Unity takes its render target from the element, not the window). Copied from Unity's Default template — the `#if USE_THREADS/USE_WASM/SHOW_DIAGNOSTICS/...` blocks are Unity's preprocessor and must stay.
2. Player Settings orientation — covers a native build of the same scene.
3. `ScreenLockView` (`Scripts/UI/`, wired in the scene by the game builder, ticked from `GameManager.Update`) pillarboxes in-game, covering hosts that ignore 1 and 2: editor Game view, iframes, a default template served by mistake. It sets `camera.rect` (which makes `camera.aspect` the locked value, so `FitCamera`/`ScreenPointToRay` follow for free) and, per Canvas, recomputes the CanvasScaler factor from the **viewport** using the scaler's own authored formula and shrinks the `Frame` child that every screen parents into. Only the wide side gets bars — a window taller than 9:16 is left alone. Verified: on a real 1080×1920 window the factor is exactly 1.0 and Frame covers the screen, i.e. no regression. Turn it off with `ScreenLockView._portraitLock` to fall back to the pre-lock layout. (The tribulation `Canvas_Flash` deliberately sits outside the Frame system — it is a full-screen flash and has no raycaster.)

There is no CLI build script; builds go through the Unity Editor (or MCP `manage_build`).

## Addressables (asset delivery)

Addressables is **selective and 100% code-driven**: `Scripts/Editor/AddressablesConfigurator.cs` computes the desired entries from the content assets and makes the groups match (menu **Tools ▸ Game ▸ Addressables ▸ Sync Groups**; also runs inside Build Game (Full) and the WebGL builds — never edit the Groups window by hand, stray entries *and* empty stray groups are deleted on the next sync). Streamed content is organized in **categories** — one group + one `AddXxx` method in `DesiredEntries` per category, so adding one is a single method plus a runtime loader. Policy: **scenes are never addressable in this project** (a scene-streamed Boot-shell architecture was tried and rejected — do not propose it again); `Main.unity` ships in the player and is always loaded, so anything the scene **hard-references** must not be addressable (it would ship twice — a build-time duplication guard errors and aborts the WebGL build if violated). Streamed content is instead **weak-referenced** from the scene via `AssetReference` fields (CODE_RULES §4 carves this exception out of the hard-`[SerializeField]` rule), loaded through **`Utils/StreamedAsset<T>`**, the reusable handle-lifecycle slot every streaming consumer must go through (newest Load wins, callback fires before the old handle is released so a live texture is never yanked, `Release()` on destroy). Two categories today: the **realm sky backdrop** (`World.SkyLayerRef`, written by SpriteBaker, streamed by `WorldBackgroundRenderer.Enter` on ascend, one bundle per world) and the **authored hero pose sheets** (`HeroView`'s `_runSheet/_poseSheet/_rangedSheet` refs, wired by the builder, streamed at `Awake` from one HeroArt bundle — sub-sprites are picked by the baker's numeric name suffix, and until they land the hero simply isn't drawn, same boot behavior as the backdrop). The builder only wires those refs when all three sheets exist (`SpriteBaker.AuthoredHeroArtComplete`); without them it wires procedural sprites hard and the HeroArt category is empty — all-or-nothing keeps the wiring branch-free. All five worlds currently point at the same authored sprite, so the group holds a single entry; re-entering it on ascend is a cheap refcount bump. Never use `WaitForCompletion()` (unsupported on WebGL). The WebGL builder does a clean `BuildPlayerContent` before every player build and lists bundles separately in the payload table (`addressables (on demand)`). `World.GroundLayer` was removed as dead (nothing rendered it since the side-scroll rework); the whole ground pipeline (PaintGround + the `bg_*_ground` PNGs) has since been deleted from SpriteBaker — each realm is sky-only now.
